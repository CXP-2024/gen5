# DP-Phys v4 preliminary validation results

## Scope

These runs validate the implementation and identify where the paired Pool is
likely to help or hurt. They are not yet the final paper-quality evaluation.

All comparisons use a 4x4x4 Torus3D with 64 nodes, one-flit control traffic,
adaptive routing, and exactly four physical VC slots per directional input
port. The private baseline uses three adaptive VCs plus one escape VC. DP-Phys
uses one private adaptive VC, two locally resident Pool slots, and one private
escape VC; ownership is movable across each E/W, N/S, or U/D pair.

The completed main matrices are:

- 120-run broad smoke sweep: four policies, three patterns, five injection
  rates, two link latencies, 3,000 cycles;
- 96-run policy sweep: four policies, four injection rates, two link
  latencies, three seeds, 10,000 cycles;
- 72-run owner-cap sweep: private baseline plus cap 2/3/4, uniform and tornado,
  three injection rates, three seeds, 10,000 cycles.
- 192-run dynamic-reversal sweep: four policies, E/W epochs 4/16/64/256,
  injection 0.3/0.9, link latency 1/8, three seeds, 10,000 cycles;
- 48-run recovery-instrumentation rerun at injection 0.9 and link latency 8,
  confirming ownership acquisition completion and latency.

Raw data are in `results_validation_v4.csv`, `results_policy_v4.csv`, and
`results_cap_v4.csv`; the dynamic data are in `results_reversal_v4.csv` and
`results_reversal_recovery_v4.csv`. Reproducible Markdown summaries are
generated by `analyze_dpphys.py`.

## Structural validation

Every extended-statistics run passed:

```text
pool_allocations = owned_pool_allocations + demand_reclaims
owner_migrations = demand_reclaims + release_handoffs
pool_reads = release_handoffs + release_keeps
sum(pool_allocations_by_direction) = pool_allocations
pool_read_conflicts = 0
```

No point deadlocked. `borrowed_peak` was one for cap 3, which matches the 3/1
owner bound. Pool write arbitration is enforced in the allocation path; no
write collision was observed in the current one-flit traffic runs. A targeted
simultaneous E/W arrival microbenchmark is still needed to exercise that rare
case directly.

`torus3d_tornado` sends every node +1 in X, Y, and Z on this 4x4x4 topology.
The new true-ingress counters therefore show Pool allocations only on the
West, South, and Down inputs, as expected. This confirms that borrowed slots
retain the real arrival direction rather than their physical host InputUnit's
direction.

## Ownership-policy result

The following is the 10,000-cycle, three-seed result at injection 0.9. Values
are means; ratios use a seed-paired equal-capacity private baseline.

| Link latency | Mode | Throughput | Throughput/base | Network latency | Latency/base |
|---:|---|---:|---:|---:|---:|
| 1 | private-v4 | 0.4489 | 1.000 | 10.46 | 1.000 |
| 1 | RTS | 0.4488 | 1.000 | 12.84 | 1.227 |
| 1 | owner-RR | 0.3138 | **0.699** | 32.08 | **3.067** |
| 1 | pressure+sticky | 0.4488 | 1.000 | 13.09 | 1.251 |
| 8 | private-v4 | 0.1564 | 1.000 | 49.37 | 1.000 |
| 8 | RTS | 0.1554 | 0.994 | 58.25 | 1.180 |
| 8 | owner-RR | 0.0680 | **0.435** | 157.03 | **3.181** |
| 8 | pressure+sticky | 0.1563 | 1.000 | 46.97 | **0.952** |

The owner-RR result is not a generic failure of round-robin switch
arbitration. The phase-RR bank scheduler remains enabled in every DP-Phys
mode. The failing policy is specifically **round-robin Pool-credit ownership
on release**: it can hand a freed credit to an inactive direction, while that
policy has no on-demand reclaim path. Tornado makes this defect visible because
each dimension is persistently one-sided.

For pressure+sticky at tornado, L=8, injection 0.9, the mean credit activity
per 10,000-cycle run was:

| Event | Mean count |
|---|---:|
| Pool allocations | 202,267.0 |
| Already-owned Pool allocations | 201,267.3 |
| On-demand reclaims | 999.7 |
| All owner migrations | 1,808.7 |
| Release-time handoffs | 809.0 |
| Release-time keeps | 201,273.7 |
| Pool reads | 202,082.7 |
| Reserved reads | 102,346.7 |

Only about 0.49% of Pool allocations required an on-demand reclaim and about
0.40% of returned credits were handed to the peer. Thus pressure+sticky is not
winning by continuously moving ownership. A small number of demand-driven
migrations establishes the useful 3/1 split, after which almost every credit
stays with the last active user. This is the desired behavior for bursts and
larger packets: mobility when needed, stability otherwise.

## Owner-cap result

At tornado, L=8, injection 0.9:

| Configuration | Throughput | Network latency | Latency/base | Peak borrowed |
|---|---:|---:|---:|---:|
| private-v4 | 0.1564 | 49.37 | 1.000 | 0 |
| pressure cap 2 | 0.1554 | 58.25 | 1.180 | 0 |
| pressure cap 3 | 0.1563 | 46.97 | **0.952** | 1 |
| pressure cap 4 | 0.1564 | 46.47 | **0.941** | 2 |

Measured as latency reduction from the private baseline, cap 3 captures about
83% of the cap-4 benefit while guaranteeing that the peer retains one Pool
credit. This supports cap 3 as the current default.

For uniform random traffic at the same point, cap 3 and cap 4 have nearly the
same behavior: 49.87 and 49.81 cycles versus the 48.32-cycle private baseline.
The extra borrowing freedom has no material value when pair demand is already
balanced.

## Where the design wins

- **Directional imbalance:** an active direction can use storage that would be
  idle on its opposite direction.
- **Long credit round trip:** the extra adaptive slot hides credit latency. In
  the tornado L=8 case, pressure cap 3 reduces network latency by about 4.8%
  without reducing delivered throughput.
- **Bursty locality:** sticky return avoids ownership churn. The observed
  migration rate is below 1% of Pool allocations in the main skewed case.
- **Safety isolation:** escape remains private, and cap 3 guarantees at least
  one Pool credit to each side.

## Where the design loses

- **Short links:** when credit latency is small, additional capacity has little
  value, while a VC can inspect only its scheduled RES or POOL bank. Tornado
  L=1 pressure latency is about 25.1% above private-v4.
- **Balanced or tie-heavy traffic:** little stranded opposite-direction
  storage exists to recover. Uniform L=8 pressure latency is about 3.2% above
  private-v4; x-opposite showed a larger penalty in the short smoke run.
- **Traffic-oblivious credit transfer:** owner-RR can strand credits at the
  inactive side and should not be used as the main policy.
- **Pool service limit:** one Pool read per pair per cycle can become the
  bottleneck even when slots are free. The benefit is a capacity/area tradeoff,
  not a universal throughput improvement.

## Remaining work before final evaluation

1. Extend the implemented time-varying E/W reversal benchmark with explicit
   multi-packet bursts to test packet-size/burst stickiness directly.
2. Run the full 0.05--1.00 injection sweep for five seeds and at least 50,000
   measured cycles, with finer points around the saturation knee.
3. Add a targeted simultaneous E/W Pool-write test.
4. Add a one-cycle owner-grant transport model; current zero-cycle grant lookup
   is an optimistic bound.
5. Add a dual-read ideal Pool ablation to isolate the exact performance cost of
   the chosen 1R/1W implementation.
6. Evaluate multi-flit packets after defining whether ownership is retained per
   packet, per VC, or per returned buffer credit.

The completed dynamic-reversal findings and their interpretation are recorded
in `reversal_results.md`.
